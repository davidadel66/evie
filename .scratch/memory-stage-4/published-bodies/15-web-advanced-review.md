## What to build

Complete web parity for the advanced review behaviors already available through the Kernel and CLI. Make identity alternatives, new definitions, temporal/correction actions, original tool authority, edit lineage and dependent batch effects understandable before approval.

## Acceptance criteria

- [ ] Render all supported candidate and effect types using the shared exact review projection, including identity alternatives, Predicate additions, temporal uncertainty, conflicting evidence and source authority.
- [ ] Support explicit owner edits and bounded batch review with visible dependencies and the frozen atomic/independent failure behavior. Preserve original extraction and edit lineage in inspection.
- [ ] Bind submission to the exact displayed preview and revisions. Scope changes, stale previews, changed sources and partial batch failures require the contractually correct user interaction.
- [ ] After accept/edit/reject, display durable outcomes consistently across web and CLI, source-session closure and reopen.
- [ ] Preserve existing origin/approval controls, source visibility and memory-storage fences. Frontend or HTTP code must not implement independent acceptance, temporal or authority rules.
- [ ] Exercise realistic frontend interactions and HTTP/Kernel persistence for ambiguity resolution, edited values, temporal corrections and mixed dependent batches, including errors and stale responses.
- [ ] Run focused deterministic cross-adapter tests and repository-required full change verification. Keep unrelated UI redesign out of scope.
