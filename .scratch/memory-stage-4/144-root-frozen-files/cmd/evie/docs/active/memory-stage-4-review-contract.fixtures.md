# Memory Stage 4 owner-review scenarios

These are acceptance oracles for [the owner-review contract](memory-stage-4-review-contract.decisions.md),
not claims that production review already exists. Use the real-SQLite Kernel
seam with scripted extraction; run matching CLI and web assertions. Source
references use the [evidence fixtures](memory-stage-4-evidence-contract.fixtures.md).
Each scenario starts independently unless specified otherwise.

Let `C1` be an unresolved candidate at interpretation/review revision `1/1`,
from committed owner evidence in source session `s1`, destination `project:p1`.
`P1` is a Kernel-created exact preview binding those revisions and scope vector
`{global:7, project:p1:12}`. Operation/generated IDs and all source hashes are
fixed fixture values. An owner review grant selects `project:p1`; no source
session or active conversation is required. Every rejected mutation below
leaves accepted graph, operations, candidate resolution, and review audit
unchanged unless the row explicitly records a successful independent group.

| ID | Action or race | Observable result |
| --- | --- | --- |
| R01: inactive source | Close/archive `s1`, release its lease, list `project:p1`, inspect C1, approve P1 with delivery `d1`, restart, inspect/replay. | C1 is visible and accepted once; exact sources remain inspectable and graph replay agrees. No session reopen, turn lease acquisition, fabricated owner source, or source-session approval event. The same old Stage 3 proposal still cannot apply without its original valid session/lease. |
| R02: exact scope | Repeat R01 with grants for `global`, `project:p2`, `workspace:w1`, and another `session:s2`; then test a session-destination candidate with an explicit grant for its own archived `session:s1`. | Wrong-scope requests disclose no candidate/source content and cannot resolve it. The explicit s1 review succeeds under its existing lineage. Project review does not include session candidates implicitly. Changing a candidate destination to global fails; permitted global Predicate creation leaves its Claim project-scoped. |
| R03: stale semantic revision | Prepare P1; another accepted operation advances project revision to 13; approve P1. | `stale_preview`, C1 unresolved. Refresh returns P2 with new digest/vector; accepting P2 requires new owner approval even if the proposition is identical. Repeat with only global Predicate revision changed: same rejection. |
| R04: changed source eligibility | After P1, install a new source-policy version whose detector excludes its source event or required assistant context. Also test a policy-version change that leaves the visible quotation eligible. | The entire preview returns `stale_preview` before any group applies; all unresolved candidates stay unresolved. Old preview/inspection never emits newly excluded bytes. Owner may reject via a new revision-bound redacted rejection preview. Missing event, hash mismatch, denied lineage, and retracted required support each have distinct safe diagnostics; a source-state revision change also makes the entire old scope vector stale. |
| R05: edited interpretation | Extractor proposed employment error correction from E15. Owner edits to real-world change with unknown exact date and the intended existing Entity. | Append interpretation 2 with parent 1 and before/after choices; retain raw generation output, original support, and earlier review history. P1 is stale. The unknown effective instant remains unknown and the candidate stays unresolved with `needs_choice`; no changed-correction lifecycle effect can be accepted yet. If the original frozen window supports an explicit effective instant, selecting it permits a fresh exact correction preview and approval. Alternatively, a further explicit edit to an ordinary assertion may be reviewed without superseding prior history. Edit text itself is not new evidence. |
| R06: reject | Prepare a rejection preview for current C1, reject with delivery d1 and reason `Not useful`. Retry d1; then accept with a new key or edit C1. | One rejected resolution/audit, no Semantic Operation or semantic revision advance. Same-key retry returns the stored rejection; later accept/edit returns `already_resolved`. A later equal generation links the preserved rejection without another operation or automatic terminal-state copy. |
| R07: repeated acceptance | Accept P1 with d1, lose the response, restart, resend the identical d1; then reuse d1 with a changed digest/action. | Identical retry returns the committed operation/result once. Changed request returns `idempotency_conflict`. A new delivery for C1 returns `already_resolved`. Current authorization/redaction still applies to returning the stored result. |
| R08: competing owner reviews | Two processes prepare C1; race accept against reject, then reverse winning order in a second fixture. | Exactly one terminal resolution and its corresponding audit/effect. Loser receives `already_resolved`; no partial graph or lost review. Race edit against accept separately: winning edit stales the old acceptance, while winning acceptance prevents the edit. |
| R09: original authority | Compile evidence fixture T01 with owner u2 and contracted clock t1; accept. Also compile E10 with owner's `Yes` and assistant question as context. | T01 sources retain `owner_statement` and `tool_observation` separately, with no invented UTC instant. E10 retains owner support and exact assistant context with authority `none`; assistant text is absent from supporting Source Links. Review, accepted inspection, and model-free replay preserve the manifest. |
| R10: independent partial batch | G1 contains proposed Entity M, new Predicate P, and dependent Claims C1/C2. G2 is an independent existing-owner preference with its own sources. Keep all preview-bound revisions, policy, bytes, and effects unchanged; inject a deterministic group-local source-validation failure for G1 at acceptance, then approve the disclosed batch. | G1 fails wholly: no M, P, Claim, Source Link, or candidate resolution. G2 commits once with its operation/audit. Result records G1's safe validation failure and G2 success in preview order. This exercises savepoint isolation, not detector reclassification or stale-preview rebasing. Retrying the same delivery returns that result and never retries G1. New G1 attempt needs a new valid preview and approval. |
| R11: dependency boundaries | G2 tries to reuse proposed M from G1, two groups write the same target Claim, a group contains a cycle, or owner deselects P while retaining its dependent Claim. | Preparation rejects independent-group labeling or invalid dependencies; combine the complete closure within bounds or prepare later against committed state. No hidden ordering assumption or orphan semantic row. |
| R12: commit failure | Inject failure after semantic rows are staged but before candidate resolution/audit, during audit insertion, and at outer commit. Inject cancellation before commit; separately lose only the successful commit response. | Every precommit failure rolls back all groups/effects/resolutions/audit. Retry revalidates and may commit once. Postcommit response loss preserves all committed rows and returns the stored outcome on duplicate delivery. Accepted replay makes zero extractor/model/tool calls. |
| R13: new support and equivalent repeat | After accepting C1, deliver an exactly equivalent suggestion in generation 2, then an equal proposition with a different required owner source. | Exact repeat links/suppresses preserved review and operation, emits no effect. Different source is a fresh attachment suggestion; owner sees the earlier decision and exact new Source Link. It remains absent from accepted support until explicitly reviewed. Owner-edited representatives survive concurrent generation delivery. |
| R14: visible conflict | Two same-name Maya Entities exist; candidate does not distinguish them. Separately propose a single-valued conflict or ambiguous correction mode. | `needs_choice` or exact conflict disclosure, no silently selected identity/winner. Choosing a distinct Entity, correction mode, or supported canonical literal appends an interpretation revision and yields a fresh explicit preview. Predicate additions cannot replace an existing global meaning. |
| R15: bounds | Prepare exactly 20 groups/64 candidate refs/256 effect records/256 KiB preview in separate fixtures, then exceed each ceiling by one unit; request inbox page 101 or use a cursor after an edit. | Inclusive exact limits pass other validation; over-limit preview returns `review_too_large` with no truncated effect/source display. Page limit is enforced; changed inbox revision returns stale cursor. An oversized atomic closure cannot be silently split. |
| R16: revoked authority | Prepare under a valid scope owner grant, then revoke its authorization before resolution. Try the old grant with a valid preview, direct client-supplied owner fields, and duplicate-result inspection. | Current authorization denies every path, without raw source or candidate-existence disclosure. No stale grant or valid digest bypasses revocation; no Stage 3 lease/source check is weakened. |

The R05 clarification preserves the existing Stage 3 changed-correction contract: an explicit effective instant is required to close the prior interval. It corrects the earlier example's jump from an unknown date to accepted lifecycle effects; it does not change correction semantics or turn review text into evidence.

R05 and R14 supply human-reviewed interpretations; deterministic tests establish
the typed edits, exact source binding, explicit choices, and effects, not an
automatic proof of semantic entailment. R10 must also run with an injected
group-local semantic validation failure and with two successful groups sharing
the starting scope vector: the first group's own revision advances do not make
the second stale, while any external revision advance or policy-identity change
before the batch rejects it all.
